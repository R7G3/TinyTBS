# ADR 0008: Проект TinyTBS.Rules

## Статус

Принято

## Контекст

Правила матча, модели контента и парсеры `Stream → модель` жили в `TinyTBS.Game` рядом с Gum и MonoGame. `internal` внутри одной сборки не отделял правила от UI. Следующие шаги (тесты правил, Android, сеть) упираются в сборку без игрового фреймворка.

Загрузка с диска уже идёт через `IFileSystem` и должна остаться в Game: у неё есть пути, user data и оркестрация сессии.

## Решение

Новый проект **`TinyTBS.Rules`** без PackageReference. В нём:

- состояние и действия матча (`MatchState`, `MatchAction`, формула урона, путь, экономика);
- поиск бота (`Ai`);
- модели и DTO карт, уровней, юнитов, строений, тем, модулей;
- парсеры, которые читают `Stream`, а не файловую систему;
- снимки сейва (`Saves.Models`), потому что `MatchState` сам их пишет и читает.

В **Game** остаются: экраны и Gum, `MatchRuntime` / `GameplaySession` / конвейер загрузки, лоадеры папок (`*Loader`, локаторы, установщик tinymod), хосты скриптов.

Зависимости: **Desktop → Game → Rules**, **Game → Engine**. Rules не ссылается на Game, Engine и MonoGame. `InternalsVisibleTo` открывает Game внутренние сеттеры сущностей матча.

## Альтернативы

- Оставить правила в Game до появления тестов — отложено раньше; граница всё равно нужна, тесты можно добавить на Rules отдельно.
- Сразу протащить `TinyTBS.Scripting.Api` в Rules — не нужно: хост скриптов в Game переводит `MatchState` в снимок API.

## Последствия

- Пространства имён правил — `TinyTBS.Rules.*`. В Game они подключены глобальными `Using`, чтобы сессия и экраны видели `MatchState` без сотен ручных импортов.
